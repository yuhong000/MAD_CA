# MAD_CA
This is a development done to satisfy the assignment portion for module “Mobile App development” under Ngee Ann Polytechnic for AY24/25”.

## Project Overview
This project is a native Android application developed using **Kotlin** and **Jetpack Compose**. It allows users to play a classic "Whack-a-Mole" game where they tap on randomly appearing targets to score points within a time limit.

### 3. Parts of the Code Generated by AI

#### Example 1: Organizing Storage Logic
Initial AI idea:
```
val context = LocalContext.current
val prefs = context.getSharedPreferences("game_prefs", Context.MODE_PRIVATE)
prefs.edit().putInt("high_score", score).apply() // Hard to manage
```

**Issues with the initial idea:**
- It mixed data storage logic with UI code (violating Separation of Concerns).
- It re-initialized the SharedPreferences object on every screen recomposition, which is inefficient.

**Final improved version**
```
// Created a separate class
class HighScoreManager(context: Context) {
    private val prefs = context.getSharedPreferences("mole_rush", Context.MODE_PRIVATE)

    fun saveHighScore(score: Int) {
        prefs.edit().putInt("high_score", score).apply()
    }
}

// In GameScreen.kt
val scoreManager = remember { HighScoreManager(context) } 
```
**Reason for improvement:**
Using a dedicated class makes the code cleaner and reusable. Using remember prevents the app from creating a new storage connection every time the frame updates.

#### Example 2: Room Database Entity
Initial AI idea:
```
@Entity(tableName = "scores")
data class Score(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val userId: Int,
    val score: Int
)
```

**Issues with the initial idea:**
- The initial schema missed the timestamp. Without it, we couldn't track when a high score was achieved.

**Final improved version**
```
@Entity(
    tableName = "scores",
    foreignKeys = [ForeignKey(
        entity = User::class,
        parentColumns = ["userId"],
        childColumns = ["userId"],
        onDelete = ForeignKey.CASCADE
    )]
)
data class Score(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val userId: Int,
    val score: Int,
    val timestamp: Long 
)
```
**Reason for improvement:**
I added a timestamp field to enable time-based sorting and the ForeignKey constraint to ensure data integrity.

#### Example 3: Stop Game Logic
Initial AI idea:
```
Button(onClick = {
    if (isRunning) {
        isRunning = false // Just stops the timer
        timeLeft = 0
    }
}) { Text("Stop Game") }
```

**Issues with the initial idea:**
- Stopping the game killed the coroutine loop immediately.
- The code to save the score was located after the loop, so it was never reached.

**Final improved version**
```
Button(onClick = {
    if (isRunning) {
        isRunning = false
        timeLeft = 0
        showGameOver = true
        
        // Manually trigger save since the loop is killed
        scope.launch {
            db.appDao().insertScore(currentUserId, score, Date().time)
        }
    }
}) { Text("Stop Game") }
```
**Reason for improvement:**
I moved the database insertion logic inside the "Stop" button's click handler to ensure the score is saved even when the user manually quits the game.

### 4. Key Takeaways and Lessons Learnt
- I learned that SharedPreferences is only suitable for simple, single-value data. Complex features (like multi-user history) require a Room Database to manage relationships and ensure data integrity using Foreign Keys.
- I learned that background tasks (like timers) must be controlled using LaunchedEffect and state keys (e.g., isRunning). Without this, timers would reset or duplicate every time the screen redrew.
- I learned to decouple UI code from Logic. Moving database operations into a DAO or helper class made the application modular, easier to debug, and allowed us to upgrade features without breaking the User Interface.
